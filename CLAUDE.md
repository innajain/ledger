# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal-finance app built on a **triple-entry bookkeeping** model (Next.js 16 App Router, React 19, Prisma 7, Postgres/Neon, Redis, Vercel Blob). `README.md` is the canonical reference for the domain model — the null-remainder storage scheme, transaction invariants, XIRR, caching keys, cron jobs, and the local/prod sync stack. Read it before touching transaction, balance, or pricing code. Note it predates two subsystems that hook into every transaction write — **cross-user linked accounts / approvals** and **push notifications** — documented in their own sections below; for those, the code is the reference. This file covers commands, conventions, and the wiring that spans multiple files.

## Commands

Package manager is **pnpm** (pinned `pnpm@11.1.2`); npm/npx are rejected. Always `pnpm <script>` / `pnpm exec <bin>`.

```bash
pnpm dev                       # next dev
pnpm build                     # prisma generate && next build
pnpm typecheck                 # tsc --noEmit
pnpm lint                      # eslint
pnpm format                    # prettier --write .
pnpm test                      # vitest run (all)
pnpm test -- normalize_txn     # single test file by name substring
pnpm test:watch                # vitest watch
pnpm analyze                   # ANALYZE=true next build (bundle analyzer)
```

Tests are colocated `*.test.ts` files (e.g. `app/_utils/normalize_txn.test.ts`); vitest resolves the `@/` alias. A pre-commit hook (simple-git-hooks + lint-staged) runs prettier+eslint on staged files.

**CI** (`.github/workflows/ci.yml`, on push/PR to `main`) is the full gate: `prisma generate` → `pnpm typecheck` → `pnpm lint` → `pnpm test` → `prettier --check`. Run those locally before pushing — CI reaches no DB (tests are pure units; a placeholder `DATABASE_URL` satisfies `prisma.config.ts`). A nightly `db-backup.yml` `pg_dump`s prod into a 30-day artifact.

**Seed script** — idempotent (wipes + recreates a single user), deterministic PRNG: `pnpm dlx tsx scripts/seed_sample_user.ts` (user `rahul` / `rahul1234`). It reads `DATABASE_URL`; point that at the unpooled Neon host to seed prod.

## Architecture conventions

- **Server-wrapper pattern**: each route is `page.tsx` (server component, data fetching only) delegating to `ClientPage.tsx` (all UI/state/effects). Follow this when adding routes.
- **Server actions** live in `app/_actions/*` (`'use server'`) when shared across routes; an action used by exactly one page is colocated in that route folder instead (e.g. `transactions/[id]/update/transactions_update.ts`, `settings/flush.ts`, `settings/validate_all_txns.ts`). They return the discriminated `ActionResult<T>` from `_result.ts` — `ok(data, msg)` / `err(code, msg)`. In catch blocks use `reportActionError(error, { action, entity? })` from `lib/action_error.ts` (unit-tested in `lib/action_error.test.ts`): it preserves `fromError`'s Prisma P2002/P2003/P2025 mapping, treats `ActionError`/Zod errors as expected control flow, and logs unexpected failures once. Expectedness is classified on the **error**, never on the caller's `fallback` code — a `fallback` of `'VALIDATION'` says how to render an unknown failure, it does not assert the failure was expected. Inside a `$transaction` callback, throw `ActionError(code, msg)` to abort the tx. Do not separately log and then call `reportActionError`, which would duplicate the event.
- **Auth & user scoping**: `proxy.ts` (Next 16's middleware equivalent — note the filename) verifies the JWT cookie and stamps a trusted `x-user-id` header, stripping any client-supplied value first. In actions, get the caller via `get_current_user_id()` / `get_current_user()` from `_actions/auth.ts` (both `react.cache`-wrapped, header-first to avoid a DB hit). **Session revocation:** tokens carry an `iat`; the proxy forwards it as `x-token-iat`, and the resolvers reject any token issued before `auth:revoke_before:<uid>` — a Redis key set on password change with a TTL equal to the token lifetime (one cached Redis read per request, fail-open on a Redis outage). **Rate limiting:** `lib/rate_limit.ts` is a fixed-window Redis limiter (fails open on Redis outage); login is capped at 10/min by IP and 5/5 min by username, signup at 5/hr by IP. **CSP:** `proxy.ts` injects a per-request nonce and sets Content-Security-Policy headers. **Every query must be scoped to `user_id`**; updates/deletes use composite `where: { id, user_id }`.
- **Pure domain logic** sits in `app/_utils/*` (e.g. `normalize_txn.ts`, `validate_line_items.ts`, `fifo.ts`, `xirr_calculator.js`, `value_timeseries.ts`) and is unit-tested. Keep the null-remainder normalization and invariant checks here, not in actions/components.
- **Decimals**: monetary/quantity columns are `Decimal(14,4)`; convert with `app/_utils/decimal.ts` (`toDecimal`), never plain JS floats.
- **Env** is validated through `lib/env.ts` (zod, `server-only`); import `env` from there rather than reading `process.env`. `lib/config.ts` holds `USER_TIMEZONE = 'Asia/Kolkata'` — all date handling is IST.
- **Prisma singleton** (`lib/prisma.ts`) is `$extends`-instrumented for profiling: it counts/times every query into the per-request `AsyncLocalStorage` context and publishes dev query events. Don't construct a second `PrismaClient`.

## Cross-user linked accounts & approvals

An `account`-type head can carry a `linked_user_id` pointing at another user. A transaction touching such a head is **shared**: each side keeps its own balanced copy, mirroring on the linked/reciprocal `account` head with **sign-flipped** `quantity`/`txn_value` (description/datetime copied verbatim), and each user chooses their own balancing lines. **Any transaction create/update/delete can therefore have approval side effects on a counterparty — account for that whenever you touch transaction write paths.**

- **State machine** is `transaction_link` (`prisma/schema.prisma`): `txn_a_id`/`txn_b_id` (either nullable — a side may delete its copy while the link lives), `pending_status` (`pending`|`approved`|`rejected`), `pending_kind` (`change`|`deletion`), and `pending_by`, which **always names whoever must act next** (null iff approved).
- **All link logic is in `app/_utils/links.ts`** (`server-only`; operates on a passed `$transaction` client — note the local `Tx` type, since `Prisma.TransactionClient` doesn't match our `$extends`-extended client). The write hooks: `create_transaction` → `create_links_for_transaction` (opens one pending `change` per counterparty); `update_transaction` (`_actions/transactions_update.ts`) → `sync_links_after_update` (re-opens only siblings whose **content signature** `linked_signature` — shared lines + txn description/datetime — actually changed; an **anchor hard-block** forbids editing shared lines while a request awaits _you_); `delete_transaction` → `prepare_links_for_delete` (approved links become `deletion` requests, the counterpart copy is the anchor); linking an account (`_actions/resources.ts`) → `backfill_links_for_account` (retroactive requests for existing txns).
- **Actions** in `app/_actions/approvals.ts`: `approve_request` / `reject_request` / revert / cancel / `accept_all_from`. Approving rebuilds the actor's copy via `build_actor_copy` — mirrored lines are locked/server-derived; the actor's own balancing lines are validated through `validate_line_items`. Every transition `invalidate_balances` on **both** users.
- **UI** is `app/requests/` — inbox (`get_inbox`, awaiting me) + outbox (`get_outbox`, awaiting them); `inbox_count` badges the nav. (A `// see docs/linked-accounts-plan.md` comment in `links.ts` points at a file not in the repo — ignore it.)

## Push notifications

Web Push (`web-push`) for the approval workflow. **VAPID keys are optional — when unset, sending is a silent no-op**, so dev and unconfigured prod run fine. `app/_utils/push.ts` `send_push_to_user` fans out to a user's `push_subscription` rows (keyed by `endpoint`), prunes ones the push service reports gone, and never throws. Domain wrappers in `app/_utils/notify_events.ts` (`notify_request_pending` / `notify_request_rejected`) are fired fire-and-forget from the approval/transaction actions. Client SW is `public/sw.js` (registered client-side); `/sw.js` and the manifest are whitelisted in `proxy.ts`. Env: `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`, plus `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (inlined client-side at build). **`app/_actions/notifications.ts`** manages push subscription CRUD (`save_push_subscription`, `delete_push_subscription`) and exposes `send_test_notification` + `send_notification_to_user` — both rate-limited via `lib/rate_limit.ts`.

## Remote MCP server (Claude / ChatGPT / Gemini)

A standard **Model Context Protocol** server at `app/api/mcp/route.ts` lets external AI clients read and write the ledger as the user, same as the web UI — every tool calls the same `app/_core/*` functions (so validation, cross-user approval links, and balance invalidation are identical), it's just another surface over the core. Built on **`mcp-handler`** (Streamable HTTP, SSE disabled); read tools carry `readOnlyHint: true`, write tools don't. The route splits across three files: `route.ts` (handler + the original read/transaction/approval tools), `_helpers.ts` (auth/formatting/resolution helpers shared by both), and `_extra_tools.ts` (`register_extra_tools` — heads/assets/templates/settings/attachments/approval-extras), plus `upload/[token]/route.ts` for attachment bytes (see Attachments below).

- **Tools**: read — `get_net_worth`, `get_holdings`, `get_balances` (optional `head` + `as_of` closing balance, `include_subheads` to cover the head's descendants), `get_asset`, `get_head` (`include_subheads` widens every figure to the subtree; `own_total` keeps the head-only value), `get_income_expense`, `list_transactions` (search/date/`head`/`asset` filters, `offset`, per-head `head_delta`), `find_similar_transactions`, `get_transaction` (incl. attachments + approval links), `list_heads`, `list_assets`, `list_requests`, `list_templates`, `get_settings`, `find_user`, `validate_my_transactions`, `get_tax_computation` (new-regime FY liability, optional `include_future` projection), `get_attachment` (inline text/JSON + image blocks); write — `create_transaction`, `create_transactions` (≤50, all-or-nothing), `update_transaction` (line_items optional — omitted keeps them), `delete_transaction` (returns a re-creatable snapshot), `pay`, `approve_request` / `reject_request` / `cancel_request` / `revert_request` / `accept_all_from`, `create_head` / `update_head` (incl. `is_active` archive, cross-user linking, `lock_date`/`clear_lock_date`, `tax_treatment`/`clear_tax_treatment`) / `delete_head`, `create_asset` / `update_asset` / `delete_asset` / `reorder_siblings` (asset scope + asset CRUD are **admin-gated** via `user.is_admin`, mirroring the web), `create_template` / `update_template` / `delete_template`, `add_attachment` (inline, ≤64 KB) / `request_attachment_upload` (everything larger) / `delete_attachment`, `update_settings`. **Write parity with the web UI is a goal — if a page can do it, MCP should too** (auth/password changes are deliberately excluded).
- **Agent-ergonomics rules** (validated by driving the local endpoint as a model would): **every emitted `datetime` is paired with a `datetime_ist`** — `text()` in `_helpers.ts` walks the serialized tree and adds it, because an instant past 18:30Z reads as the previous day and inputs are IST, so a model round-tripping the Z string slips a day. **Line items accept `head` (the name reads return) as well as `account`, and `quantity: null` as well as an omitted one** — the read/write shapes have to match, since the server `instructions` tell the model to read first and copy. Arg names are aliased rather than duplicated in spirit: `find_similar_transactions.search` (= `query`), `add_attachment.id` (= `transaction_id`), `accept_all_from.from_user` (= `from`, which everywhere else means a start date). `resolve_ref` failures carry a **"Did you mean"** edit-distance suggestion and cap candidate lists at 25 per type. Keep these invariants when adding tools.
- **Agent-safety contract** (born from real agent feedback): `create_transaction`/`create_transactions` accept `idempotency_key` (unique per user — replaying returns the existing txn instead of double-posting; race-safe via the DB constraint); a **near-duplicate guard** (same account, same net flow, ±36h) rejects creates with the matching id unless `force: true`; `dry_run: true` validates and echoes the server-derived remainder lines without writing; every mutating transaction tool returns the **post-write balances** of the touched accounts; deletes return the full deleted snapshot. Dates accept dd-MM-yyyy **or** yyyy-MM-dd everywhere (`parse_day`); `get_head`/`get_asset` line items paginate (`line_items_limit`/`_offset`, `from`/`to`).
- **Attachments — a tool argument cannot carry a file.** `add_attachment` takes content inline (`content_text` / `content_base64`), which means the bytes have to be produced by the _model_, so anything past tens of KB is both slow and silently lossy: one wrong base64 character yields a corrupt file that still uploads cleanly and reports a plausible size. It therefore **refuses above 64 KB** (`MAX_INLINE_ATTACHMENT_BYTES`) and names the alternative. For real PDFs and photos, **`request_attachment_upload`** mints a one-time capability URL and returns a ready-to-run `curl_command`; the agent PUTs the file to `/api/mcp/upload/<token>` and the bytes go disk → network without passing through the conversation. The token _is_ the credential, because an MCP client holds its bearer token privately and can never forward it — so the grant (`mcp_attachment_upload`) is stored **sha256-hashed** like `mcp_oauth_code`, expires in 10 minutes, is single-use via an atomic `consumed_at` claim, and is bound to one user + one transaction so a leaked URL can't be redirected at another ledger. A claim that fails verification is **released**, so the same URL retries instead of being burned by a transient blob error. Content type is decided by **sniffing magic bytes** (`app/_utils/attachment_content.ts`, unit-tested), never by trusting the declared header or the extension; `text/plain` and `application/json` have no signature, so those are validated by strict UTF-8 decode (and `JSON.parse`), which also stops a binary blob entering as text. `/api/mcp/upload/` is whitelisted in `proxy.ts` **as its own narrow prefix** — don't widen that to `startsWith('/api/mcp')`, which would open every future sub-route by default.
- The read tools aim for **parity with the web UI** — every page's computed values (asset/head detail incl. XIRR + FIFO cost basis, period income/expense, hierarchical list values) are reachable; heavy compute and large payloads sit behind opt-in flags (`include_line_items` / `include_timeseries` / `include_values`). The handler also ships server-level **`instructions`** telling the connected model to consult the user's transaction history (via `find_similar_transactions`) and reuse their existing heads before creating/updating rather than re-asking for every detail. Head/asset args accept an id **or** a name (exact case-insensitive, then unique-substring; a failed match returns the valid names, an ambiguous one lists the candidates); the authenticated `user_id` comes from `extra.authInfo.extra.userId`. Note `get_head`/`list_*` reimplement a couple of page rollups on `compute_balances_core(uid)` because the page versions resolve the user from request context, which MCP bearer auth doesn't populate.
- **Auth is self-hosted OAuth 2.1 + PKCE** (clients like Claude's web/mobile connectors only support OAuth, not static bearer headers). All token logic is in **`lib/mcp/oauth.ts`** (`server-only`): clients self-register via DCR, codes/tokens are stored **sha256-hashed** (`mcp_oauth_client` / `mcp_oauth_code` / `mcp_access_token` in `prisma/schema.prisma`), access tokens last 1h with 90-day rotating refresh tokens. **No new env** — tokens are opaque random, not JWTs.
- **Endpoints**: discovery at `app/.well-known/oauth-{authorization-server,protected-resource}/route.ts` (RFC 8414/9728); `app/api/oauth/{register,authorize,token}/route.ts`. `authorize` is the only browser-facing one — it reuses the normal `ledger_token` login cookie (bouncing to `/login?next=` when absent — see `safe_next` in `app/login/ClientPage.tsx`) and renders a CSRF-protected consent page. **All of `/.well-known/*`, `/api/oauth/*`, and `/api/mcp` are whitelisted in `proxy.ts`** (they do their own bearer/cookie auth).
- Connecting a client: add `https://<host>/api/mcp` as a custom connector; it auto-discovers the flow via the 401 `WWW-Authenticate` on `/api/mcp`.

## Agent-safety features (web + MCP)

Historical (or, for a future `cutoff`, projected) closing balances come from **`closing_balance_core`** (`balances_core.ts` — any head type, book value, IST end-of-day), surfaced as `get_balances as_of` (MCP) and the `AsOfBalance` card ("Balance on a date") on account/allocation head pages. A cutoff beyond now also pulls in scheduled (`is_future`) transactions dated before it, projecting the balance forward instead of excluding them (`NOT_FUTURE` still applies for a past/present cutoff) — see Future transactions below for the per-line-item breakdown behind that projection. The near-duplicate guard **`find_possible_duplicate`** lives in `transactions_core.ts` and backs both the MCP guard and the create form's amber warning (`transactions/create/check_duplicate.ts`). Other web wiring from the same pass: delete-undo (`delete_transaction_with_snapshot` → sessionStorage `ledger_undo_delete` → toast on the transactions list; attachments are not restored), user-scoped `settings/validate_my_txns.ts` (ValidationSection), and client-side "Show more" pagination of line items on head/asset detail pages.

**Head scope (this head only / with sub-heads)**: a parent head usually holds nothing itself — its money sits in its children — so its detail page reads ₹0 with an empty holdings grid and an empty line-items list. The `?scope=subtree` search param (a `ScopeToggle` link pair, rendered only when the head has children) re-scopes the _whole_ page to the head plus its descendants: totals, FIFO-derived `Current investment`, holdings, line items (each tagged with the sub-head it sits on), XIRR, the value chart, future-transaction sufficiency, and `Balance on a date`. It is a URL param, not component state, because each scope is a different server-side query — only the chosen one is ever computed, and the view is shareable. **The details card carries exactly one scope's figures** — never a "this one only" row beside a "with sub-accounts" one, which left the reader unable to tell which total the holdings and line items below belonged to; the other scope is one click away and the sub-heads card still lists each child's total. Both scopes are computed live from line items rather than the cached-balance rollup, which is what lets either offer a FIFO cost basis (`compute_head_rollup` therefore returns only the per-child totals). `own_total` is the head-only balance, never displayed but used for UPI settlement and the "you owe" line, since a sub-account's money settles against that sub-account. FIFO queues are keyed by head _and_ asset so a sell in one sub-account can't close a sibling's lots. A subtree series is cached under its own `<head_id>:subtree` frozen key, never sharing the head's own key — same head, different answer; **`invalidate_timeseries` therefore climbs ancestors** (`get_ancestor_head_ids` in `head_tree.ts`, the pure mirror of `get_subtree_head_ids`, unit-tested including parent cycles), because a line item on a head changes the "including sub-heads" series of every head above it, none of which the write names. Without that climb the subtree view could not be cached at all, and it was recomputing the whole day-by-day walk plus historical NAV lookups on every click. `ScopeToggle` gives each link its own `useLinkStatus` spinner: a search-param change on the same route segment is a soft navigation, so Next never renders the route's `loading.tsx`, and without it the page sits unchanged with the clicked button not even looking pressed for the whole render. MCP parity: `get_head`/`get_balances` take `include_subheads`.

**Reconciliation lock**: `accounting_head.lock_date` (account type only, nullable) freezes verified history — every write whose line items would touch that account on/before the lock's IST day is rejected (`app/_utils/lock_date.ts`, `assert_no_locked_lines`, unit-tested). Enforced in all four `transactions_core` write paths **and** the approval bypass (`build_actor_copy` in `links.ts`, deletion approvals in `approvals_core.ts`) — an incoming approval into your locked period errors until you move the lock back. Set/cleared per account on the head edit page, via `update_account_core`'s trailing `lock_date` param (`Date | null | undefined` = set/clear/keep), or MCP `update_head`; `get_head`/`list_heads` expose it and the account detail page shows a locked-through banner. Workflow: verify an account against the bank (`get_balances as_of`), then advance its lock.

**Future transactions**: `transaction.is_future` (nullable-free boolean, default `false`) marks a scheduled/draft transaction that never affects balances, net worth, XIRR, or income/expense until converted to real. The shared `NOT_FUTURE` filter (`app/_utils/future_txn.ts`) is spread into every balance/list query that must exclude them; lock-date checks are skipped while a transaction is future (`transactions_core.ts`) and cross-user link creation is deferred until conversion. `convert_future_transaction_core` flips `is_future` to `false`, at which point the usual mirror/approval flow for linked accounts kicks in as normal. `app/_utils/future_balance.ts`'s `compute_future_sufficiency` is the pure, unit-tested algorithm behind the "Future transactions" section on head detail pages: it walks a head's future line items (one row per line item, not per transaction) in effective-datetime order, carrying a running per-asset `Prisma.Decimal` balance forward from the head's current real balance, and marks each row `sufficient` (balance stays ≥ 0) with its resulting `balance_after` — a line item already dated in the past is "overdue" and excluded from the walk, getting `null` for both. Web: the sufficiency badge only shows on debit (negative) lines, colored red/green like the real line-items list, capped at `max-h-96 overflow-y-auto`; the home page's "Upcoming transactions" card lists the soonest ones with a link to `/transactions?future=future`. **Due** is the one cross-surface marker: `is_future_txn_due` (`future_txn.ts`, unit-tested) is true for anything dated on or before the **end of today IST** — the whole day, so something scheduled for later today is already due — and every surface computes it server-side off a single `now` per render, so no two rows straddling midnight disagree and the badge can't hydrate differently. It badges the home card, the future transactions list, and the head page's future section, where it is deliberately orthogonal to `compute_future_sufficiency`'s "overdue" (dated before _now_, excluded from the walk): a line due later today is both `due` and still carries a sufficiency verdict. MCP parity: `create_transaction`/`update_transaction` take `is_future`, `convert_future_transaction` promotes one, `list_transactions` takes `future: 'exclude' | 'only' | 'include'`, `get_head`'s `include_future_transactions` surfaces the same per-line-item `balance_after`, and every future row on `list_transactions`/`get_transaction`/`get_head` carries the same `due` flag (omitted on real transactions) so an agent never has to re-derive the IST day boundary.

## Transaction tags

A **transaction tag** is a user-defined label over whole transactions — "Eating out", "Goa trip". Many-to-many: a transaction can be in several tags, and a tag holds many transactions (`transaction_tag` + the `transaction_tag_member` join row, both cascading).

- **It is descriptive only.** Membership never touches balances, net worth, XIRR, income/expense, FIFO or the null-remainder normalization, so no write in `app/_core/tags_core.ts` calls `invalidate_balances` or `invalidate_timeseries` — that is exactly what makes tagging a cheap overlay you can re-cut at will. Don't wire a tag into a computed figure without revisiting that.
- **Tags are never mirrored across a cross-user link.** Each side labels its own ledger; `build_actor_copy` updates the existing copy in place, so an approval leaves the actor's own labels alone, and editing tags never re-opens an approval. Deleting a tag deletes the label only — its transactions are untouched.
- **Totals**: a tag's figure is the same signed book flow the transactions list shows per row (net over the transaction's account lines). Future (`is_future`) members are counted but never added up — they move no balance anywhere else, so folding them in would make one number disagree with all the others. `summarize_tag_flow` (`app/_utils/tag_rollup.ts`, unit-tested) is the definition; the `/tags` list computes the same shape in SQL (`tag_rollup_sql`) rather than pulling every tagged transaction's line items into JS, with FILTER clauses mirroring it clause for clause — keep the two in step.
- **Write paths**: `create_transaction_core` takes `tag_ids` in its opts (bulk create validates ownership once per batch via `load_own_tag_ids`); `update_transaction_core` takes a trailing `tag_ids` where `undefined` keeps and an array replaces (`[]` clears), matching how `line_items` behave. The delete snapshot carries `tag_ids`, so delete-undo restores the labels (unlike attachments).
- **UI**: `app/tags/` (list with per-tag totals, detail with its transactions and a remove-from-tag control), the `TagPicker` chip multi-select on the transaction create/edit forms — which can create a tag inline, since you invent the bucket while posting the entry that needs it — tag chips on the transaction detail page, tag names beside the time on each list row, and a `?tagId=` filter on `/transactions` (both the Prisma and the raw-SQL amount-sort branch).
- **MCP parity**: `list_tags` / `get_tag` / `create_tag` / `update_tag` / `delete_tag` / `add_transactions_to_tag` / `remove_transactions_from_tag` / `set_transaction_tags`, plus a `tags` arg on `create_transaction`/`create_transactions`/`update_transaction`, a `tag` filter on `list_transactions`, and tag names on `list_transactions`/`get_transaction` rows.

## Income tax computation

The `/tax` page and MCP `get_tax_computation` derive a **new-regime** Indian income-tax liability straight from the ledger — **always live, never stored**, so a back-dated transaction moves it.

- **`accounting_head.tax_treatment`** (nullable enum, income/expense heads only) declares how a head counts: `salary_17_1`, `perquisite_17_2`, `exempt`, `other_sources`, `stcg_slab`, `stcg_111a`, `ltcg_112a`, `gift_56_2_x`, `tax_paid`, `not_income`. Both `create_account_core` and `update_account_core` guard the **post-update** state — a classification can't be stranded on a non-`income_expense` head.
- **`app/_utils/tax_compute.ts`** is the pure, unit-tested slab/rebate/cess engine; the FY rules live in a config constant (`FY_2026_27`), so an annual rate change is a data edit, not a code change.
- **`app/_core/tax_core.ts`** does the FY rollup on an explicit `user_id`, so the page and the MCP tool share one implementation — any divergence between `/tax` and `get_tax_computation` is a routing bug, not a rounding one. It **normalizes each transaction in full before cutting line items on their effective date**: `normalize_line_items` derives the null-remainder leg from the account lines and throws if handed a filtered subset. `serialize_tax_result` is the JSON-safe shape both consumers render.
- **Unclassified heads with a non-zero net are excluded and reported**, never silently assumed zero — both surfaces tell you to classify them first. The "project to year end" toggle (`include_future` in MCP) folds scheduled (`is_future`) transactions in.
- Classification is edited per head on `/tax` (`set_tax_treatment.ts`) or via MCP `create_head`/`update_head`; `get_head` and `list_heads` both expose the current value.

## Data export & dumps

Four download routes share collectors in `app/_utils/db_export.ts` and pure, unit-tested builders in `app/_utils/{csv,zip,xlsx,sql_dump}.ts` (ZIP and `.xlsx` OOXML are hand-rolled — no new deps). Table names and `WHERE` clauses are **static literals**; the lone bound param is the user id (no injection surface) — keep it that way if you extend `USER_TABLES`/`FOREIGN_KEYS`. `collect_user_export(user_id, excluded?)` is caller-scoped (and pulls referenced `asset` catalog rows even though `asset` has no `user_id`); `collect_full_dump()` walks every base table. Routes: `/api/export` (CSV-per-table ZIP) and `/api/export/xlsx` (one linked workbook, FK cells hyperlinked) both drop `password_hash` via `DEFAULT_EXCLUDED_COLUMNS`; `/api/dump` is the **caller-scoped** SQL dump (keeps every column so it restores); `/api/admin/dump` is the whole-DB SQL dump behind `require_admin` (`app/_actions/auth.ts`, backed by `user.is_admin`). Surfaced in `app/settings/` (`DataSection.tsx`, plus admin-only `AdminSection.tsx`). Note `/api/dump` used to be unscoped — it leaked all users' rows and hashes; don't reintroduce an unscoped data route.

## Runtime observability, profiling & dev tooling

Pages are wrapped with `profile()` (`lib/metrics/`); metrics land in `server_metric`/`slow_query`/`web_vital` (fire-and-forget) and the same non-user-identifying measurements are emitted as Sentry `ledger.*` metrics/span attributes. `proxy.ts` generates and returns `x-request-id`; the logger mixin attaches that ID plus the active Sentry trace/span to every log within a profiled request. `persistMetrics` emits one `request.completed` structured log per render. Disable the page wrapper with `PROFILING=off`. In dev, a query toaster surfaces each DB/Redis op via SSE at `/api/dev/queries`; silence with `DEV_QUERY_TOASTS=off`.

Sentry initialization is split by runtime: `instrumentation-client.ts` (browser, router transitions), `instrumentation.ts` (Next registration and `onRequestError`), and `sentry.{server,edge}.config.ts`. `app/error.tsx` and `app/global-error.tsx` capture React boundary failures. `next.config.ts` uploads source maps, deletes them after upload, and tunnels browser events through the public `/monitoring` path. **Three channels carry raw text and are all deliberately off — do not add any of them back.** Session Replay (recorded DOM); `consoleLoggingIntegration`, which forwards console calls as Sentry Logs; and the default `consoleIntegration`, which attaches them as breadcrumbs. The last one is the trap: Sentry 11 added it to the default integrations where Sentry 10 had not, so an upgrade turns it on by itself. `withoutConsoleBreadcrumbs` in `sentry.data-collection.ts` filters it out of all three runtimes — and the server passes `integrations` as a **function**, because an array is merged into the defaults, which is exactly how it gets back in. All three matter for the same reason: recorded DOM and raw console text (a React hydration-mismatch message quotes the rendered text) carry account names and amounts straight past the server-side redaction. For the same reason the browser drops Sentry Logs outright via `beforeSendLog: () => null` — Sentry 11 removed the `enableLogs: false` that used to say this, and logs are now always on, so the flag's absence is not consent. Traces sample at 10% via `SENTRY_TRACES_SAMPLE_RATE` / `NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE`; `pinoIntegration` forwards `warn` and above only, so the per-render `request.completed` info log stays on stdout. Per-request measurements ride the page span as `ledger.*` attributes — don't reintroduce a parallel `Sentry.metrics.*` fan-out, which emitted ten unsampled series per render for numbers `server_metric` already stores. Successful mutations use `audit()` from `lib/logger.ts`; it hashes the actor into `actor_ref` and may include only non-sensitive operation metadata (counts, booleans, enum type). PII collection is `dataCollection` in `sentry.data-collection.ts` (Sentry 11 replaced the old `sendDefaultPii: false` flag with it) — one shared constant across the three runtimes, with **every field explicitly off**, because each one defaults to _collecting_: stack-frame locals, bound query parameters with returned rows, cookies, headers, bodies. Here a local is an amount and a query parameter is an account id, so a new field appearing in a future version defaults the wrong way and must be added there. GraphQL and gen-AI are denied too though nothing instruments them yet, so enabling one later is not also a decision to ship its payloads. Verify a Sentry upgrade by sending a deliberate error through a deployed build and reading the envelope (`client.on('beforeEnvelope', …)`), not by trusting the config; never log raw user IDs, usernames, IPs, descriptions, amounts, account/asset names, filenames, URLs, or auth/push credentials; never add user ids to Sentry spans or metrics, and never bypass logger redaction.

Health checks are split: `GET /api/health` is liveness — public, uncached, and it must touch **no** dependency, which is what makes leaving it unauthenticated safe. `GET /api/health/ready` is the Postgres/Redis probe; it is rate limited (10/min per IP through `lib/rate_limit.ts`) rather than cached, because a cached readiness probe reports health it never observed. Both must stay read-only, uncached, and free of credentials, connection details, row data, or raw dependency errors. Sentry is optional when `NEXT_PUBLIC_SENTRY_DSN` is unset; `SENTRY_AUTH_TOKEN` is a build secret and must never be exposed to client code or committed.

**Env exception for bootstrap files.** `instrumentation-client.ts`, `instrumentation.ts`, `sentry.{server,edge}.config.ts`, and `next.config.ts` read `process.env` directly instead of `lib/env.ts`. This is deliberate, not drift: `lib/env.ts` is `server-only` (importing it into the client bootstrap breaks the build) and throws on a bad parse (which in the server bootstrap would crash instrumentation _before_ Sentry can report the crash). Every other module still imports `env`. `sentry.data-collection.ts` is shared by all three and therefore stays import-free for the same reason — nothing `server-only` may reach it.
